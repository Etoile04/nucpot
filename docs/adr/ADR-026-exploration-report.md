错误模式：E1 域包漏进 registry → alembic 产出 DROP TABLE（生产级）/ 测试侧 NoReferencedTableError 或 _strip_dangling_fks 静默剥 FK（潜伏级）；E2 域间 import 漂移 → 循环 import（database.py:183 延迟 import 是压力信号）；E3 同表双定义 → SQLAlchemy「Table already defined」（kg_node.py 现存案例）；E4 删闸计数漏根 → scripts/e2e 现场 ImportError 且 CI 不红（护栏外崩坏）。

【implementation 内化什么】每域包内化：域内 ORM 类、域内枚举/常量（RE_EXTRACTION_STATUSES、EXTRACTION_STEP_TYPES、ONTOLOGY_VERSION_STATUSES 等）、域内 TYPE_CHECKING 类型引用；core_models 内化：base 四件套、review 行为契约（ReviewMixin/ReviewStatus/VALID_TRANSITIONS + Review 审计表——Review 必须进 core_models 的 re-export 面，api/v1/review.py:31 直达消费）、user(RBAC)/source(来源标注)（与 ADR D2 core 清单对齐）；material/ontology_version 以跨域 FK 入度 5/4 为据上收；unit/classification_level/ontology 以领域主数据论据并入（frontier #1 双档）。

【seam 位置】seam 1（metadata）：migrations/env.py:30,44 与 tests/conftest.py:44,354-449——两个同构消费方，收敛到 registry；seam 2（消费 interface）：src 28 处包外聚合 + 168 处包外直达 + tests 116/231 次 + apps/api/scripts 8 文件 + 根级 scripts 5 处 + e2e/seed_hub.py:12——五个消费根，其中 scripts/e2e 三根在 PR CI 护栏外；seam 3（守门）：pyproject [tool.importlinter] 三契约 + 五根 rg 计数器。

【adapter】无运行时 adapter（module 重组非进程分离）：过渡 adapter = 瘦内核 re-export 层（自灭式，conflict.py:1-16 证明 shim 可行也证明无回收闸会滞留）；守门 adapter = import-linter（layers: models.base < models.core_models < 8 域包；independence: 域互不 import；forbidden: 消费方直达包内文件）；回归 adapter = 表集合快照测试 + 公共面双面测试（__all__ 面 + 直达名字面）+ 五根计数器。

**替代方案（已否决）**：替代方案：不拆包——models/ 保持 45 文件平铺，仅做「抽 base.py + 清死代码（kg_node/conflict 并名）+ import-linter 按文件名清单分组约束」。否决理由：(a) ADR-026 D2/Phase 2 要求「模块以包为单位、经 entry points 注册」，entry points 的发现单元是包；平铺目录没有包级聚合面，不拆包则 Phase 2 后端注册单元无从建立，本候选失去服务对象；(b) import-linter 契约只能手写 45 个模块名清单，每新增模型文件都要改契约——契约本身成为下一个热改冲突点（__init__.py 90 天 9 次改动已证明聚合层就是冲突点）；(c) 域包路径是 ADR Phase 1 CI 路径矩阵与 CODEOWNERS 的天然锚点，平铺目录无法按路径选测。另一激进变体「一步删聚合 __init__、全仓改直达 import」亦否决：改写面（src 28 处聚合 + 168 处直达 + tests 116/231 次 + scripts/e2e 及根级 scripts 9+ 文件）与包移动耦合在一个 PR，违反 ADR-026 D5 strangler-fig「每步行为可验证、可回退」。

**替代方案（已否决）**：真实替代案：不拆 conftest，只做「测试文件按簇归位 + CI 路径矩阵」（即 ADR-026 Phase 1 表格的字面最小口径）——保持单一 conftest，靠 `pytest tests/api/v1/ -o addopts=` 按目录选测拿墙钟收益。否决理由（本版依 collect-only 实测改写，撤回原「装配面钉死 7 分钟线」的夸大推断）：① 装配面实测仅秒级——`uv run pytest --collect-only -q` 8584/8767 collected in 7.86s，收集期已含 conftest.py:43 的全局 app 装配（45 router）与全部 432 模块 import，钉不死分钟级验收线；② 真正的墙钟常数在 per-test schema 面——db_session 是 function 级全库 create_all/drop_all（conftest.py:354/:383），186 个消费文件 × 每测试一次的固定开销不随选测目录缩小，只有簇级 schema 面才砍得动（且那步依赖 C1）；③ locality 是 Strong 评级的本义——单一 conftest 下改任何 fixture 波及全仓（一改全红），模块作者没有自己的测试面，且两个全局 app 突变 autouse（:183-318）的语义永远全仓共享、无法按簇收窄（E1 类风险永久存在）。此替代能拿 CI 时长的一部分收益、拿不到 locality 与 per-test 常数的另一部分。更激进的「每模块独立 tests 包 + 独立 pyproject/uv 工程」（仓内 polyrepo）否决：与 ADR-026 D1/D2 直接冲突（agent 舰队成本×N、共享 schema 切断），且 432 文件大爆炸迁移不可回退，违背 D5 strangler-fig。

## C5 · Nav 注册 seam：每模块贡献导航项

**复核**：独立复核通过（14 条证据全部核实）

**形状（shape）**：interface＝导航项 manifest 与装配函数，纯数据无 JSX：NavItem { href, label, group: 'primary'|'more'|'user'|'admin', order?, adminOnly?, flagKey?, requiresAuth? }，聚合 barrel 导出 assembleNav(session) -> 分组视图模型。不变式：(1) 组内 href 唯一（NFM-5068 重复项病根的直接不变式）；(2) href 必须对应真实路由（防死链；断言脚本须展开 (dashboard) 括号目录与动态段，实测 18 个动态段目录）；(3) adminOnly 条目对非 admin 会话不可见；(4) flagKey 条目在旗标快照未解析/求值失败时隐藏（对齐 flag-service fail-closed）——此不变式属未来 flagKey 步骤，且它要求装配签名届时扩为 assembleNav(session, flagSnapshot)：flag-service 是 fetch 后端异步求值 + 模块级缓存（flag-service.ts:11-14），同步纯函数承诺以「当前无 flagKey 条目」为前提，快照入参是显式预留位；(5) group 语义属 IA 裁决（NFM-4984 站点地图：一级 vs 更多 vs 管理员菜单，Nav.tsx:10-34 注释史），模块只能贡献条目、不能自行挪组。错误模式：重复 href（NFM-5068 已发生过）、指向已删路由的死链（middleware.ts:17-23 的 /extraction 死条目证明此类漂移真实存在）、admin 条目泄漏给普通用户、label 缺失。implementation 内化：desktop/mobile 两份手写清单（Nav.tsx:232-313 与 :413-494，含 12 处 {isAdmin && ...}）收敛为单一数据 × 渲染器；权限过滤（isAdmin 判据 Nav.tsx:98）从条目定义移到装配时统一执行；激活态规则（isMoreActive 前缀匹配 / isMoreLinkActive 精确匹配，Nav.tsx:52-58）收为纯函数。渲染器内 class 按「渲染位置 × variant × admin/normal」矩阵逐形态保留（实测至少 4 形态：desktop primary :141-145、desktop 面板普通 :235 vs admin :264、mobile 列表 :416、mobile admin :445——不是两份 class map，字面两份必丢 admin 黄色或面板 hover:bg）。dropdown 开合状态、click-outside 留在渲染器——是渲染关注点，不进 manifest。seam 位置：apps/web/src/lib/navigation/（类型 + 聚合 barrel + 装配函数），Nav.tsx 原地降级为 seam 之上的纯渲染器（ADR-NFM-4076 D2「原地深化」在此翻译为「原地降级」——不挪 Nav.tsx 文件本身）。adapter 有四：(1) Nav.tsx 渲染器（唯一消费者，root layout.tsx:48 挂载）；(2) 各模块 route 目录的 nav.ts 数据贡献文件（locality：模块条目随模块走；admin 组例外——集中放 app/admin/nav.ts 并注明 lightrag 条目跨家族认领，见 frontier Q4 取舍）；(3) 聚合 barrel（静态 import 显式聚合，镜像后端 api/v1/__init__.py + main.py:301-355 的现状风格，对齐 ADR-026 D2「Phase 2 前维持显式聚合」）；(4) flag-service adapter（未来 flagKey 条目，/benchmarks 为首个候选实例，经 flagSnapshot 入参接入）。leverage：6 个近期 IA 工单从改 509 行共享组件变为改各自模块的数据文件；desktop/mobile 漂移这一整类 bug（NFM-5068）从「e2e 事后守卫」升级为「结构性不可能」。

**替代方案（已否决）**：替代方案：集中单一注册表 apps/web/src/config/navigation.ts（全部模块条目写在一个文件，Nav.tsx 变纯渲染器）。优点真实：实现最小、无聚合 barrel、一次类型检查、迁移一步到位。否决理由（按强度排序，第一条独立于未兑现前提）：(1) churn 仍是集中式——同样 6 个工单仍全改同一文件，只是冲突面从 509 行缩到 ~60 行数据，locality 零增益；(2) 与 ADR-026 D2「App Router 路由目录即模块边界（现状已如此）」（ADR-026:54）方向相悖；(3) 集中文件无法被 module owner 认领——【前提未兑现】此条依赖的按目录 CODEOWNERS 尚不存在：实测 .github/CODEOWNERS 仅 4 条哨兵脚本规则（NFM-5715，.github/CODEOWNERS:12-15），模块所有权是 ADR-026 Phase 1 的未来物；若 Phase 1 形态改变（如放弃按目录所有权），此条需重估，但前两条理由独立成立，否决结论不变。另一个也考虑过的极端——构建时 fs 扫描 route 目录自动发现 nav.ts（类 Next.js 内部 codegen）——一并否决：引入隐藏控制流与额外构建步骤，agent 舰队与 Turbopack 行为都不友好，且「忘记注册导致功能不可达」从编译期可见错误变成静默缺失。折中：迁移第 1 步先落集中文件（作为中间态），第 3 步再机械拆散到模块目录——集中文件是脚手架不是终点。

## C3 · 路由器深化：业务逻辑退到 service interface 之后（含 C8 任务派发补齐）

**复核**：独立复核通过（12 条证据全部核实）

**形状（shape）**：deepened module 的形状（router 深化：HTTP 薄层 + service interface 承接业务）

【interface】router 只保留 HTTP 面：路径/参数解析、鉴权 Depends、4xx/5xx 映射、响应信封。业务面收敛为 6 个 service interface：
1. KG 查询 interface（新）：structured_search / graph / node_relations / node_detail / semantic_query（含回退策略与 RAGProviderSelector 构造——kg.py:151-202 整段内化），输入纯参数 + AsyncSession，输出 Pydantic schema；VALID_NODE_TYPES 校验（400 语义）以领域异常形式抛出。
2. potentials 文件 interface：download(potential_id, index) → FileResolution 三态（本地文件/307 重定向/远端流）+ upload(potential_id, filename, content)；RemoteFileStream 归宿 = potential_file_resolver（potentials.py:34-41 已 import 其 5 个名字，流式 adapter 是第 6 个名字，locality 成立）；client 构造以 factory 注入为测试 seam。
3. 白名单单一事实源：ALLOWED_EXTENSIONS 只在 upload_service 定义一次（router/其余消费 import）。
4. blog 内容 interface：read_markdown(slug)/enrich_post + list_published/get_published_by_slug 落 blog_post service（写侧 get_content_dir 单源已存在，读侧并入同模块）。
5. literature 读侧 interface：11 处 select 聚簇约 5 个查询函数（list_sources/get_source/figures/stats/delete 依赖）落 literature_service 读侧或独立查询模块（与 1428 行写侧的切分随实施定）。
6. 派发 interface（C8）：task_dispatcher.dispatch（已存在，4 消费方）+ 新增任务名常量表（celery_app 内单点定义），task_routes/beat/dispatch 调用点引用同一常量——Phase 2 包移动时任务名只改一处。
不变式：I1 HTTP 契约冻结——OpenAPI 路径/状态码/响应 schema/信封不变，全部现有 API 测试不改断言即绿；I2 路由器无 ORM——api/v1/*.py 不出现 select(/session.execute（守门计数器单调降）；I3 派发单缝——src 内除 task_dispatcher 与 celery_app 外无 .delay(/apply_async/send_task；I4 白名单单源——ALLOWED_EXTENSIONS 定义处数=1；I5 providers 包不得三态长存（零消费者+测试养护是负资产）。
错误模式：E1 HTTPException 下沉进 service（FastAPI 依赖泄漏，CLI/管线复用即炸——kg.py:220-227 现状在 router 内抛 400，搬运方式需约定）；E2 NFM-1142 重演——interface 设计成与端点一一对应的一次性形状，下一个消费者出现时再被摘除（kg_query_service 孤儿是实证）；E3 任务名字符串漂移——Phase 2 包移动时 task_routes 硬编码路径未跟 → worker「Received unregistered task」（celery_app.py:84-99 注释记载的正是这类事故）；E4 RemoteFileStream 生命周期丢失——_stream_cm 引用注释（potentials.py:82-88）记载过 httpx.StreamClosed 截断 200 事故，移动时重演；E5 测试 patch 点漂移——test_potential_file_proxy.py:188 全局 monkeypatch httpx.AsyncClient，不随移动改 patch 点则测试失效或测到假象。

【implementation 内化什么】kg：5 条 inline SQLAlchemy 语句 + 3 个映射器 + _NODE_TYPE_MAP 可视化映射 + 语义回退；potentials：RemoteFileStream + 存储解析分支 + 下载计数容错 + 上传写盘/hash/extra 变更 + 白名单；blog：路径安全检查 + frontmatter 解析 + 公开读查询 + enrich；literature：11 处 select；celery：任务名常量表 + HPC failover 任务体委派既有 hpc_orchestration + audit 任务体的 asyncio 线程边界样板（三次重复，抽一次）；auth：User 直查下沉 auth_service，extraction 域门移出共享内核。

【seam 位置】seam A（查询）：router↔service 函数签名（纯参数入、Pydantic 出）；seam B（流/存储）：RemoteFileStream 与 httpx client 构造之间——client factory 注入；seam C（派发）：task_dispatcher.dispatch + 任务名常量表；seam D（守门）：三只 rg 计数器（router 内 select 计数、src 内 .delay 旁路计数、ALLOWED_EXTENSIONS 定义处数）挂路径过滤 CI——pyproject 现无 import-linter（亲验 rg 无命中），契约式守门为可选项非前置。

【adapter】无进程级 adapter（同进程深化，OpenAPI 面不变即外部零感知）。测试 adapter：流测试从全局 monkeypatch httpx.AsyncClient 改 patch service 模块 client factory（test_potential_file_proxy.py:188 现状是全局替换）；xfail 的 extraction API 测试（test_extraction_api.py:39,80）按 dispatch seam 重写。守门 adapter：rg 计数器脚本（沿用 batch1/2/3 路径过滤 CI 先例）。providers 若接线则 CompositeProvider 是 potential_service 之后的第二实现（PotentialProvider protocol 已在 base.py 定义）；若删除则无 adapter。

**替代方案（已否决）**：替代方案：「不建 service 层，随 Phase 2 模块包化整体搬运」——把 kg.py/potentials.py 等 580/430 行混杂体原样搬进各自模块包（module = router + helpers），靠包边界而非层级强制 locality，改动量小且零行为风险。否决理由：(1) C8 并入部分根本不经过 router——celery 任务名硬编码、rag_audit 旁路、celery_app 内联 HPC failover 都在 services 层内部，包化方案覆盖不到，dispatch 单缝仍缺；(2) ADR-026 D2 明文 module = APIRouter + services + schemas，services 缺位则 Phase 2 搬运的是混杂体，模块内两层不分，Phase 3 部署单元拆分（worker 独立发布）时任务名常量表与查询能力无落点；(3) 测试面将继续只打 HTTP 端点（重、慢，xfail 累积——test_extraction_api.py:39,80 两个 xfail 是 router 级 mock 脆弱的实证），service 面测试无法建立，Phase 1 的 CI 路径矩阵收益打折；(4) 已分叉的白名单（30 vs 21）与 local.py 平行查询拷贝在「整体搬运」中会被原样冻结成两份模块内事实源。

## C6 · 契约安家：packages/ 承载生成式类型，替代手写漂移

**复核**：独立复核通过（16 条证据全部核实）

**形状（shape）**：deepened module 的形状（契约从散装手写 deepening 为单一安家 module）

【module 定位】packages/contracts = ADR-026 D2「core 接口与显式契约」的前端投影 + Phase 2「core 接口变更须过契约测试」的载体。它把今天散在 apps/web 的 270 行手写镜像（locality 烂：改一个后端字段要在 20+ 文件里人肉找镜像）收拢为一处生成源——leverage 点：后端 Pydantic 改动经 openapi→typecheck 自动传导到 51（types.ts 消费）+31（api-client 精确 import）个文件，NFM-1555 式 404 与 NFM-4343 式 union 不再靠人肉 keep in sync。spike 已证原料完整可导：183 paths / 204 operations / 378 schemas。
