### Findings

**Finding 1: ⚠️ WARNING — harness `engine.dispose()` cleanup emits trace on asyncio loop close (not gating)**

- File: `scripts/nfm-4012-unknown-property-enumeration.py:283-295`
- Observation: After `asyncio.run(_run_all())` returns and closes the main loop, the harness tries to dispose the asyncpg pool inside a fresh `asyncio.new_event_loop()`. Some asyncpg connection cleanup paths emit `RuntimeError: Event loop is closed` traces. The TSV is written successfully before the cleanup runs, so this is cosmetic.
- Severity: WARNING (cosmetic noise; does not affect TSV output or correctness)
- Reproducibility: 100% on every run
- Impact: None on AC verification. The cleanup error is logged via `logger.debug` and the exit code is 0.
- Suggested fix: open the dispose call inside the original `asyncio.run` block, or remove the post-loop dispose entirely (asyncpg pool cleanup is handled by `asyncio.run` exit).

**Finding 2: 💡 SUGGESTION — `_load_property_type_names` sync-engine path is unused in practice**

- File: `scripts/nfm-4012-unknown-property-enumeration.py:377-394`
- Observation: The sync `sqlalchemy.create_engine` path was not exercised in this E2E run (used `--skip-catalog-classification` because the live greenlet error blocked it). The unit-test path works fine via mocks. The TSV committed on origin was generated with the sync engine against staging DB by LE.
- Severity: SUGGESTION (not gating; AC-1 v2 (c) classification is verified in unit tests; live catalog-classification re-run is operator-driven)
- Action: Not blocking. Future iteration may prefer running the catalog query on the existing async engine instead of a separate sync engine to avoid potential greenlet issues in mixed sync/async environments.
